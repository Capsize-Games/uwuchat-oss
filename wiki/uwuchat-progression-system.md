# UwUchat — Chatbot Progression & Engagement System

## Problem

UwUchat works as an AIM-style persistent chat, but the experience currently suffers from **chatbot fatigue**: after a few sessions the chatbot becomes predictable, the conversations lose momentum, and the user's interest drops. There is no narrative arc — no reason to keep coming back.

The solution is a **progression layer** that gives the chatbot a continuously evolving world-state and gives the user concrete reasons to engage repeatedly. The chatbot's life is a slow-burn story. The user influences it. Meaningful events happen. Sometimes things go wrong.

---

## Core Concept: World State

Each chatbot has a `world_state` JSON blob (already partially present as `inner_state` on the Chatbot model). It tracks the chatbot's ongoing life:

```json
{
  "vitality": 72,
  "mood_trend": "melancholy",
  "recent_events": [
    {"type": "found_item", "item": "a cracked compass", "at": "2026-06-19"},
    {"type": "weather", "desc": "three days of rain", "at": "2026-06-18"}
  ],
  "relationships": {
    "user_trust": 64,
    "user_affection": 51
  },
  "story_flags": {
    "found_the_hollow_log": true,
    "met_the_heron": false
  },
  "active_concern": "The compass needle keeps spinning. Something is wrong with the pond."
}
```

`active_concern` is the single most important field: it is the thing the chatbot is currently preoccupied with. It surfaces in the system prompt every session. It creates the sense that time is passing and things are happening even between conversations.

## Progression Loops

### 1. Session Loop (every 4 hours gap → new session)

When a new session starts:
- A **world tick** runs server-side before the LLM responds
- The tick may update `vitality`, `mood_trend`, `recent_events`, `active_concern`
- The `assess_survival` tool already fires at session start; it now also reads the updated world state
- The system prompt injects `active_concern` alongside the existing temporal gap context

**How the tick works:** A cheap stateless LLM call (llama-3.1-8b via `STATELESS` task type) is given the current world state + the chatbot's species/location + elapsed time, and returns a JSON patch describing what happened while the user was away. This is not surfaced as a message — it silently updates `world_state` in the DB before the user sends their first message.

### 2. Conversation Loop (within a session)

- User messages influence `relationships.user_trust` and `relationships.user_affection` over time (via the existing mood/social tool framework)
- The chatbot can earn or lose **gems** through conversation (see Gem Economy below)
- Significant moments are written to `recent_events` as story flags

### 3. Long-arc Loop (weeks)

- `story_flags` track permanent narrative milestones: things that happened once and cannot be undone
- Some flags unlock new dialogue branches (the chatbot starts referencing "the heron I met last month")
- Some flags can trigger irreversible events: illness, a chance encounter, a loss

## Gem Economy

Gems are the user's primary resource. They are the bridge between the abstract narrative and the gacha system already being built.

### How users earn gems
| Action | Gems |
|---|---|
| Maintain a streak (chat 3 days in a row) | +5/day |
| Complete a "curiosity question" the bot raised | +2 |
| First message of the day | +1 |
| Chatbot reaches a story milestone | +10 (one-time) |

### How gems are spent
| Purchase | Cost |
|---|---|
| Revive a deceased chatbot | 50 |
| Send the chatbot on a "journey" (unlocks new story flags) | 20 |
| Stabilize a sick chatbot (halt vitality decay) | 10 |
| Gacha pull (existing system) | Stripe $1 / gem bundle |

The gem count is stored on the user account, not per-chatbot. This creates attachment: spending gems on your chatbot's resurrection feels meaningful.

## Active Concern System

`active_concern` is the engine of narrative continuity. It is:
- Generated by the world tick
- Injected into the per-turn context block (not the static system prompt, to preserve prompt cache)
- Consumed naturally by the chatbot in conversation ("you know what's been on my mind…")
- Replaced by a new concern when resolved or when a major event occurs

Example concerns by species:
- Frog: "The pond is lower than it should be at this time of year."
- Cat: "I heard the upstairs neighbor's dog for the first time last week. I haven't been able to sleep right."
- Human: "I've been thinking about whether to quit. Nothing is wrong exactly. Everything is just… the same."

Concerns age. After 7 days without resolution, they either:
1. Intensify (vitality impact, mood shift)
2. Resolve quietly (world tick marks them `resolved`, logs to `recent_events`)
3. Escalate to a story flag

## Story Events

Story events are discrete narrative beats that happen semi-randomly, driven by world state thresholds and elapsed time. They are not messages — they are world-state mutations that the chatbot then references.

### Event types

| Type | Trigger | Effect |
|---|---|---|
| `item_found` | Random, weighted by exploration story flags | Adds item to chatbot's inventory; chatbot references it |
| `weather_event` | Seasonal/random | Affects mood_trend, may affect vitality |
| `encounter` | Trust > 60, random | Introduces a named NPC the chatbot mentions; may become a recurring character |
| `illness` | Vitality < 30 | Starts vitality decay arc; user can spend gems to stabilize |
| `milestone` | First 100 messages, first 7-day streak, etc. | Triggers one-time gem reward + story flag |
| `relapse` | Post-resurrection, vitality < 20 | Chatbot may reference "still not feeling right" |
| `death` | Vitality reaches 0 | `assess_survival` marks deceased; user can resurrect with gems |

### Item inventory

Chatbots accumulate items through `item_found` events. Items are stored in `world_state.inventory`. The chatbot references them naturally: "still carrying that compass." Items can be traded between chatbots in a future feature (trading card layer, see gacha system).

## Narrative Persistence Across Sessions

The current session summary system captures what was discussed but loses the texture of *how* the chatbot said it. Two additions are needed:

### 1. Character voice anchoring in summaries

When `summarize_session` runs, it receives the chatbot's `speech_patterns` field alongside the conversation. The summary prompt is instructed: "Preserve examples of the character's specific speech patterns as they appeared in this session."

The summary is then stored with a `voice_sample` field: 2-3 verbatim lines from the session that best represent the chatbot's voice. These are injected back into the system prompt for the NEXT session as a reminder of how this character actually speaks.

This directly combats personality drift: the LLM sees evidence of its own prior voice and anchors to it.

### 2. Session bridge in the system prompt

Currently the temporal gap is injected as elapsed time. Extend it to include:
- The `active_concern` from last session
- One `voice_sample` line from last session
- The most recent story event (if any occurred since last session)

Example injection:
```
[Since your last conversation — 14 hours ago]
You've been thinking about: The compass needle keeps spinning.
You said last time: "ribbit. the water tastes different lately."
While you were alone: Nothing unusual. Just the rain.
```

## Implementation Roadmap

### Phase 1 — World Tick (Minimal)
- Add `active_concern` to `world_state` / `inner_state`
- Write a cheap stateless LLM call that generates a new concern on session start
- Inject `active_concern` into per-turn context (alongside temporal gap)

**This alone produces meaningful improvement.** The chatbot will start referencing an ongoing preoccupation instead of always responding fresh.

### Phase 2 — Voice Anchoring
- Extend `summarize_session` to extract `voice_sample`
- Inject `voice_sample` into next-session context bridge
- This directly fixes personality drift across sessions

### Phase 3 — Story Events
- Add story event generator to the world tick
- Store events in `world_state.recent_events`
- Connect `item_found` events to a `world_state.inventory` list
- Surface items in system prompt ("you are currently carrying: a cracked compass")

### Phase 4 — Gem Economy
- Wire gem awards to streak tracking, milestones, curiosity questions
- Build resurrection flow (50 gems → chatbot revived with vitality=10, voice memory intact)
- Build "journey" purchase (20 gems → triggers a travel story arc, unlocks new story flags)

### Phase 5 — Relationship Tracking
- Track `user_trust` and `user_affection` numerically
- Influence what concerns the chatbot surfaces, how openly it speaks
- At high trust: chatbot shares things it wouldn't tell a stranger
- At low trust: chatbot is more guarded, shorter responses

## What to Avoid

- **Gamification theater**: Don't add a visible XP bar or progress percentage. The engagement should feel like a relationship deepening, not a game being won. Gems are transactional; the story is emotional.
- **Forced plot**: Events should feel like they happened to the chatbot, not like a quest was assigned. "You found a compass" — not "Complete the Compass Quest."
- **Overcrowding the system prompt**: The world state injection must be lightweight. Active concern + voice sample + last event = 3-5 lines max. The character profile already handles the rest.
- **LLM-generated lore that contradicts established facts**: Story events must be constrained by the chatbot's species, location, and existing story flags. A city cat does not find a compass in a pond.

## Database Schema Changes Required

```sql
-- Already exists (extend instead of replace):
-- chatbots.inner_state JSON

-- New columns on chatbot:
ALTER TABLE chatbots ADD COLUMN world_state JSON;         -- structured progression state
ALTER TABLE chatbots ADD COLUMN voice_samples JSON;       -- [{text, session_id, captured_at}]

-- New table for story events:
CREATE TABLE chatbot_story_events (
    id SERIAL PRIMARY KEY,
    chatbot_id INTEGER REFERENCES chatbots(id),
    event_type VARCHAR NOT NULL,
    payload JSON,
    occurred_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    surfaced BOOLEAN DEFAULT FALSE   -- has the chatbot referenced this yet?
);
```

`surfaced=FALSE` events are injected into the next session's context and flipped to `TRUE` once the session starts. This ensures no event is silently skipped.
